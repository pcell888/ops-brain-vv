# 架构问题分析与优化方案

## 一、已发现的关键问题

### 1. 巨型文件 / God Object（最严重）

| 文件 | 行数 | 问题 |
|------|------|------|
| `compat_tracking.py` | **2149** | 单文件包含追踪启动/列表/快照采集/效果分析/完成追踪/取消/趋势/复盘报告/案例搜索/看板等 **16 个端点** + 大量内联业务逻辑（LLM 调用、指标计算、DB 操作、方案沉淀），严重违反 SRP |
| `compat_diagnosis.py` | 818 | 兼容层本应薄转发，实际内含完整业务逻辑 |
| `diagnosis.py` | 796 | 流程编排 + 进度推送 + 钻取 + 历史查询全挤一个路由文件 |
| `execute.py` | 585 | 节点函数包含部门解析、任务构建、规则推送、券活动、审批等至少 5 个职责 |

### 2. 大量重复代码

- **`_slim_anomalies` / `_slim_indicators`**：在 `diagnose.py` 和 `generate.py` 中**完全复制粘贴**
- **`_get_admin_accounts`**：在 `diagnose.py`、`generate.py`、`track.py` 中各写一份
- **`_uri_to_conninfo` / `_postgres_uri_to_conninfo`**：`db_init.py` 和 `graph.py` 中各有一套几乎相同的 URI 解析
- **LLM 调用模板**（构建消息→ainvoke→解析 JSON→日志 usage probe→merge usage）在 `diagnose.py`、`generate.py`、`track.py`、`compat_tracking.py` 中重复 **4 次**
- **DB 连接样板**（`AsyncConnection.connect(_conninfo())`）在 `compat_tracking.py` 中出现 **15+ 次**，每个端点自行打开连接
- **部门解析逻辑**：`execute.py` 中 `_dept_resolve` 和 `_build_execution_tasks` 各自维护一套关键词匹配 `["销售", "运营", "客服", ...]`

### 3. 数据库层无抽象 / 无连接池

- **无连接池**：每次请求都 `AsyncConnection.connect(conninfo)` 创建裸连接，高并发下 PG 连接数爆炸
- **无迁移工具**：DDL 以字符串拼 `CREATE TABLE IF NOT EXISTS` + 手动 `ALTER TABLE ADD COLUMN IF NOT EXISTS`，分散在 `db_init.py` 的 8 个 `ensure_*` 函数中
- **每个 ensure 独立开关连接**：`startup` 里 8 次 `ensure_*` 就建 8 次连接
- **兼容层 compat_tracking.py 直接内联原始 SQL**，无 repository 抽象

### 4. MCP stdio 子进程架构的脆弱性

- `_sessions` / `_shutdown_events` / `_bg_tasks` / `_init_locks` 全是**模块级全局可变状态**
- 子进程崩溃后 `_sessions.pop` 但没有自动重建机制，后续调用直接 `RuntimeError`
- `mcp_call` 的 120s 超时 + 30s 启动超时，但无健康检查/心跳，无优雅降级

### 5. 兼容层膨胀

7 个 `compat_*.py` 文件总计约 **5000 行**，其中 `compat_tracking.py` 单独 2149 行。这些不是薄代理，而是**重新实现了大量业务逻辑**（指标采集、LLM 复盘、快照计算），与 agent node 中的逻辑并行存在。维护两套等价但不同的实现，是 bug 温床。

### 6. 状态管理问题

- `DiagnosisState` 用 `dict | None` 大量使用（如 `anomalies: list[dict] | None`），失去了类型安全
- `progress_cache`、`running_tasks` 是进程内 `dict`，无法跨进程/多实例，部署第二个实例即失效
- `emit_progress` 里直接 `from src.api.deps import progress_cache` 做延迟导入，agent 层对 API 层产生了**反向依赖**

### 7. 硬编码看板数据

`compat_tracking.py` 末尾的 `get_dashboard_funnel`、`get_dashboard_teams`、`get_dashboard_ranking` 返回**写死的假数据**，正在线上被前端消费。

### 8. 配置 / 密钥管理

- `Settings` 用 `@lru_cache` 永久缓存，运行时改 `.env` 无法生效（需重启进程）
- CORS `allow_origins=["*"]` 无限制
- `on_event("startup"/"shutdown")` 已是 FastAPI 过时 API，应改用 lifespan

### 9. 测试覆盖薄弱

现有测试仅覆盖 `calculator`、`indicator_push_rules`、`deadline_fields`、`diagnosis_page_no` 等辅助函数。**核心流程（agent nodes、API routes、MCP 调用、DB 交互）无任何测试**。

### 10. 可观测性 / 日志

- `tracing.py` 前 250 行是 LLM usage 提取工具函数，后 50 行才是 OTEL 初始化——两个完全无关的职责
- 模块顶层执行 `setup_logging` / `setup_tracing`（`main.py` L34-36），import 即产生副作用

## 二、优化方案

### Phase 1: 消除重复 / 提取公共模块（低风险、高收益）

| 动作 | 具体 |
|------|------|
| 提取 `src/core/db_pool.py` | 基于 `psycopg_pool.AsyncConnectionPool` 的全局连接池单例，替代所有裸 `AsyncConnection.connect` |
| 提取 `src/core/uri_utils.py` | 统一 `_uri_to_conninfo`，`graph.py` 和 `db_init.py` 共用 |
| 提取 `src/agent/utils.py` | 放 `_slim_anomalies`、`_slim_indicators`、`_get_admin_accounts`、`_message_text` 等所有 nodes 共享的工具 |
| 提取 `src/core/llm_caller.py` | 封装 `build→invoke→parse JSON→record usage` 的标准化 LLM 调用流程，4 处调用点缩为 1 行 |
| 提取 `src/core/dept_resolver.py` | 统一部门关键词匹配 + 人员分配逻辑 |

### Phase 2: 拆分巨型文件（中风险）

| 文件 | 拆分方案 |
|------|---------|
| `compat_tracking.py` | 拆为 `tracking_snapshot.py`（采集快照）、`tracking_lifecycle.py`（启动/完成/取消）、`tracking_report.py`（复盘报告）、`tracking_cases.py`（案例搜索）、`tracking_analysis.py`（趋势/效果分析） |
| `execute.py` | 提取 `rule_task_builder.py`（5.2.3 规则任务构建）、`dept_resolver.py`、保留 `execute.py` 仅做编排 |
| `diagnosis.py`（路由） | 拆分钻取逻辑到 `drill_down.py`，进度构建到 `progress.py` |

### Phase 3: 数据库层重构（中风险）

| 动作 | 具体 |
|------|------|
| 引入 Alembic | 已完成：启动流程仅执行 Alembic，移除运行时手写 DDL/`ALTER TABLE ... IF NOT EXISTS` |
| 统一 Repository 模式 | 已完成：`compat_tracking` 路由层内联 SQL 全量迁移至 `src/core/compat_tracking_repo.py` |
| 连接池 | `psycopg_pool.AsyncConnectionPool` 作 FastAPI lifespan 管理 |

### Phase 4: 架构改进（较高风险，可渐进）

| 动作 | 具体 |
|------|------|
| 消除 agent→API 反向依赖 | `emit_progress` 改为纯事件发布（EventBus / callback 注入），不 import `src.api.deps` |
| MCP session 自动重建 | 子进程崩溃后自动重连，加健康检查 |
| 进度/任务状态迁移到 Redis | `progress_cache`、`running_tasks` 从进程内 dict 迁移到 Redis，支持多实例部署 |
| 兼容层瘦化 | 兼容 compat 路由改为薄适配器，调用同一套 service 层，而非重复实现业务逻辑 |
| FastAPI lifespan | 替换过时的 `@app.on_event("startup"/"shutdown")` |
| 删除硬编码假数据 | `funnel`/`teams`/`ranking` 端点要么对接真实数据，要么返回 `501 Not Implemented` |

### Phase 5: 测试补全

| 优先级 | 覆盖目标 |
|--------|---------|
| P0 | `diagnose_node`、`generate_solutions_node`、`execute_plans_node` 的单元测试（mock MCP + LLM） |
| P0 | `compat_tracking` 核心端点的集成测试 |
| P1 | `BizAPIClient` 重试/超时/错误处理的测试 |
| P1 | MCP session 生命周期测试 |
